# anviod/edgeCore — 参考报告

> **调研日期**：2026-08-17
> **仓库**：https://github.com/anviod/edgeCore
> **技术栈**：Go（后端）+ Vue3/Vuetify（管理界面）+ bbolt 存储 + expr-lang 规则
> **定位**：轻量级工业边缘网关（制造/能源/楼宇），主打工业级稳定性
> **契合度**：★★★★（本轮调研与本项目最契合的参考）

## 一、仓库概览

edgeCore 是与本项目定位几乎重叠的成熟参考：**RK3588 单板 + 统一采集 + 边缘计算 + 北向上送 + 稳定性工程**。

关键事实（README/文档/论文核实）：
- 单二进制、`CGO_ENABLED=0` 静态编译、无运行时依赖；**128MB 内存 / 1GB 存储**；x86_64/ARMv7/ARM64；裸机/systemd；无需云端、无需容器
- 实验硬件即 **RK3588（Cortex-A55/A76）**——与目标板一致
- 13 种南向工业协议统一采集；10ms 级调度内核

**核心架构**（调度驱动，文档 `architecture-overview`）：

```
南向驱动(13协议) → ScanEngine(调度内核) → ShadowCore(内存影子·单一事实源 COW)
                                            → ShadowBridge 扇出
                                                ├→ 边缘规则 / 虚拟影子派生
                                                ├→ 持久化(历史)
                                                └→ 北向(MQTT/Sparkplug B/OPC UA/BACnet + store_forward)
```

配套：嵌入式 Profile（Pipeline Worker，去外网依赖）vs 完整 Profile 双轨；EAN 2.0 边缘智能体网络（MQTT/NATS + capability + invoke + 心跳 + 权限审计）。

## 二、值得借鉴（为什么）—— 本轮最高优先

### 1. ShadowCore（内存影子 · 单一事实源）
对应本项目「特征常存 + 看门狗状态 + 切片元数据」应统一成**一个内存状态层**。
- 借鉴：纯内存 COW 快照 = 单一事实源，UI / 边缘计算 / 北向都从 shadow 读，ShadowBridge 扇出；
  配置 SoT（bbolt）与运行时 SoT（内存）分离。
- 为什么：我们目前看门狗快照 / 触发状态 / 切片 meta 分散在各模块，各自持有；引入一个
  `ShadowCore`（如 `09_采集层` 之上加状态层）能让 UI、触发、切片、上送共用同一份事实，
  避免不一致与重复计算。

### 2. ScanEngine（调度驱动内核）
对应本项目「快路径每帧 + 慢路径按状态门控」需要一个**调度器**，而不是硬编码循环。
- 借鉴：ScanEngine 拥有时间/资源/任务状态，驱动只是纯执行器；P99 调度 lag <150ms（10k tag）。
- 为什么：我们 M1 收尾的「慢路径按过程状态门控」正是"谁来调度慢路径窗口"的问题；
  ScanEngine 的"调度器拥有任务状态"是正确分层，可直接映射为快/慢路径调度器。

### 3. DataPipeline 扇出 + 限速背压（去重/窗口合并/限速）
对应 M1「特征日志 + 上送」的管道化 + 鲁棒性 R13（背压/队列有界）。
- 借鉴：ShadowBridge → DataPipeline 去重/合并/限速，再扇出到规则/历史/北向。
- 为什么：我们特征日志与切片上送需要统一的扇出管道，限速背压正好解决"慢路径积压 → 内存爆"。

### 4. 熔断 + 失败 tag 冷却降级 + store_forward
对应鲁棒性 R10/R11 + 数据飞轮上行通道。
- 借鉴：per-device circuit breaker + 失败点位 cooldown(SKIPPED 标记) + NorthboundCache 断网续传。
- 为什么：比我们 InputQuality 门控更进一步——异常点位被标记后**冷却退避**而不是反复重试，
  这是现场 7×24 长稳的关键；断网续传保证数据飞轮不丢数据。

### 5. 指标门控 + Soak 长稳回归 + CI 五 gate
对应 08 鲁棒性验收门禁（24h soak）的工程化做法。
- 借鉴：内置 SLA 指标（lag/miss deadline）+ Soak 回归 + CI 门禁，稳定性"可观测、可验证"。
- 为什么：我们 08 清单的验收标准正是"24h soak + 混沌注入 + 无静默失败"；edgeCore 给出
  了把稳定性做成**出厂指标门控**的完整实践（diagnostics/sla_warnings）。

### 6. 嵌入式 / 网关双 Profile
对应本项目「两阶段板卡策略」（RK3588 开发 → A733 量产）。
- 借鉴：嵌入式精简 Profile（Pipeline Worker，去外网依赖、资源可控）vs 完整 Profile。
- 为什么：开发板（性能盈余）跑完整能力、量产板（A733 低配）跑精简 Profile——和我们的
  板卡分层完全同构，可参考其 Profile 划分边界。

## 三、不需要借鉴（为什么）

| 点 | 为什么不需要 |
|----|-------------|
| Go 技术栈 | 我们是 Python 算法栈，仅借鉴架构理念不借代码 |
| 13 种 PLC/工业协议驱动 | 我们只采三相电流 + 可能 VFD 遥测，不需要全协议栈 |
| EAN 2.0 边缘智能体网络 / AI Agent / MCP | 多网关 Agent 协同场景我们没有，过于超前 |
| OPC UA / BACnet 北向服务器 | 我们不需要做北向服务器，MQTT/HTTP 即可 |
| Vue3 管理界面 | 当前非重点，已有 HTML 看板 |

## 四、结论

**借鉴度 ★★★ 高（本轮最高契合）**。它是"RK3588 单板 + 采集调度 + 内存影子 + 稳定性工程"
的成熟参考，与本项目定位几乎重叠。最该抄的四个点：
① ShadowCore 单一事实源；② ScanEngine 快慢路径调度器；③ DataPipeline 扇出+背压；
④ 熔断/失败降级 + Soak 指标门禁。其中 ① ② ④ 直接对应本项目 M1 收尾与鲁棒性余项。
