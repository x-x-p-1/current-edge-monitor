# zhangkaigod2000/BetterIOT — 参考报告

> **调研日期**：2026-08-17
> **仓库**：https://github.com/zhangkaigod2000/BetterIOT
> **技术栈**：C#/.NET Core + MQTT + ZeroMQ + LiteDB
> **定位**：适合在 ARM 和 X86 边缘计算设备上运行的工业设备数据采集系统

## 一、仓库概览

BetterIOT 是 .NET Core 写的工业数据采集网关，跑在 Ubuntu/Windows 的 ARM/X86 上。
核心设计（从代码中核实）：

```
IDrive<T> 驱动抽象（DeviceConn/GetData/DeviceDiscnn 三件套）
   → 大量 PLC 驱动：西门子 S7/PPI/FetchWrite/MPI、三菱、欧姆龙、松下、
      基恩士、富士、台达、LSIS、ModbusRTU、DLT645、CNC(Haas)、国标 GBxfxy
   → ConfigBase 配置驱动（每设备一个 JSON 配置）
      ↓
ZeroMQ 内部总线（XPub/XSub）解耦：采集 → 存储 → 上送
   → MQTT 上送（断线重连 + 心跳）
   → LiteDB 本地缓存 + Sended 标记 + 定时清理（每 10 分钟删已发送）
   → DriveStatusService 驱动在线状态监控（心跳）
```

## 二、值得借鉴（为什么）

### 1. `IDrive<T>` 采集驱动抽象 + 配置驱动 —— 遥测接入层
对应 TODO「按工况打标签」/「慢路径按状态门控」需要的 **VFD/PLC 工况信号接入**。
- 借鉴：每类设备一个驱动类，统一 `DeviceConn/GetData/DeviceDiscnn` 生命周期，配置 JSON 驱动。
- 为什么：我们目前只有电流通道；将来要按工况（负载/转速/温度）打标签，需要一个
  "电流 + 遥测"统一的采集抽象，否则各自为政。这套接口模式可直接照搬成 Python 抽象基类。

### 2. MQTT 断线重连 + 心跳（heartBeat）
对应上行通道稳定性 + 鲁棒性 R11（心跳）。
- 借鉴：连接断开自动 `Connect()` 重连 + `heartBeat()` 保活。
- 为什么：边缘设备网络不稳定，断线重连 + 心跳是上行通道的底线能力。

### 3. LiteDB 本地缓存 + Sended 标记 + 定时清理
对应 M1「特征日志常存」+ 鲁棒性 R7（内存/磁盘有界）。
- 借鉴：数据先落本地库，`Sended` 标记已上送，定时删已发送 → **本地缓存有界且不丢数据**。
- 为什么：我们切片 `.npz` + 未来特征日志需要"先本地、后上送、可清理"的落盘策略，
  这套"标记 + 定时清理"防止磁盘无限增长（对齐 R7）。

### 4. ZeroMQ 内部总线解耦
对应未来采集/诊断/上送多模块解耦。
- 借鉴：采集、存储、上送通过消息总线解耦，各模块可独立启停。
- 为什么：与 freeioe 的 skynet 服务拆分同理——模块解耦便于故障隔离与替换。

### 5. DriveStatusService 驱动在线监控
对应采集链路健康监控。
- 借鉴：后台服务跟踪每个驱动的最后心跳时间，判断在线/离线。
- 为什么：多通道/多驱动时需要一个统一的"采集健康看板"，这是现成做法。

## 三、不需要借鉴（为什么）

| 点 | 为什么不需要 |
|----|-------------|
| C# / .NET Core 技术栈 | 与 Python 算法栈不一致，仅借鉴模式不借鉴代码 |
| 大量 PLC 协议驱动（西门子/三菱/欧姆龙…） | 我们目标是被测电机电流，不直接采 PLC；除非将来接 VFD 遥测，只需建抽象不需要全套驱动 |
| 串口轮询式采集（Thread.Sleep 轮询） | 我们是 16kSPS ADC 高速流式，采集模式完全不同 |
| 单机 JSON 配置无版本管理 | 我们用 config.yaml 数据契约驱动，比它更规范 |

## 四、结论

**借鉴度 ★★★ 高**。最值得抄：
① 驱动抽象 + 配置驱动（遥测接入层）；
② 本地缓存 + Sended 清理 + MQTT 断线重连（特征日志/上行通道）。
与 freeioe 的借鉴点高度互补：freeioe 强在缓冲/升级，BetterIOT 强在驱动抽象/本地持久化。
