# zhangedwin/aiotec — 参考报告

> **调研日期**：2026-08-17
> **仓库**：https://github.com/zhangedwin/aiotec
> **技术栈**：C++ + lighttpd Web + 瑞芯微 NPU + Apache-2.0
> **定位**：融合「RTU 采集 + 视觉 AI」的开源边缘计算网关（rk3568/rk3588）
> **契合度**：★★ 中（理念印证为主）

## 一、仓库概览

AIOTEC Gatewaybox 是新一代开源边缘计算系统：**创新融合 RTU 系统（多协议物联采集）与视觉边缘计算系统（NPU 视觉 AI）**，B/S 架构可视化配置。C++ 实现、适配 arm64（rk3568/rk3588）、Debian11、单二进制 + 内置 lighttpd Web。

核心能力（README 核实）：
- **物联中枢**：多协议融合接入 MODBUS / DLT645 / IEC104 / PLCS7 / OPCUA / GB28181 / ONVIF / zigbee 等
- **视觉分析**：瑞芯微 NPU 毫秒级推理——火焰/未戴安全帽/人脸/车牌/人员跌倒/聚集/流量计数；支持 Qwen3-VL 大模型
- **数据上报**：采集数据 / 视频流 / 分析结果上送平台；IEC104 应用 + **断网续传**
- **组态系统（SCADA）**：拖拽图形模块做设备监控/数据展示/自动化控制
- **规则引擎**：新增联动场景
- **误报反馈**：「反馈并提交误报情况，帮助我们进一步改善算法精确度」
- 其他：视频录像、人脸黑白名单、大模型预测维护

## 二、值得借鉴（为什么）

### 1. 误报反馈 → 改善精度（数据飞轮的落地形式）
- 借鉴：产品特性"反馈误报 → 改善算法精确度"，即人工反馈回流训练。
- 为什么：这正是我们「数据飞轮」理念（触发切片 → 人工确认 → 积累标签 → 重训）的**现成落地形态**，
  证明"误报反馈闭环"是真实产品特性而非理论。

### 2. 断网续传（数据上行通道）
- 借鉴：采集/分析结果上送支持断网续传。
- 为什么：freeioe / BetterIOT / edgeCore 都含断网续传——第三次印证"断网不丢数据"是边缘网关行业标配，
  我们数据飞轮上行通道应内置此能力。

### 3. 多协议融合接入（统一驱动抽象）
- 借鉴：MODBUS / DLT645 / IEC104 / PLCS7 / OPCUA 等统一接入。
- 为什么：第三次印证"统一驱动抽象"（同 BetterIOT / LotusBridge / edgeCore）——将来接 VFD/PLC 遥测时同一套模式。

### 4. 组态系统（SCADA 拖拽监控）
- 借鉴：拖拽图形模块做设备监控/数据展示/自动化控制。
- 为什么：我们看板目前是 HTML；产品化阶段可参考组态化的拖拽监控与联动。

### 5. 瑞芯微 NPU 毫秒级推理 + 大模型边缘部署
- 借鉴：RK3588 NPU 毫秒级视觉推理 + Qwen3-VL 大模型边缘部署实践。
- 为什么：我们 M3（RKNN NPU 推理）是同一平台（RK3588 NPU），它的边缘部署实践有参考。

## 三、不需要借鉴（为什么）

| 点 | 为什么不需要 |
|----|-------------|
| 视觉算法（火焰/人脸/车牌等） | 与电流信号诊断无关 |
| C++ 技术栈 | 我们 Python 算法栈 |
| GB28181 / ONVIF 视频协议 | 我们不做视频采集 |
| Qwen3-VL 视觉大模型 | 视觉场景，与电流诊断无关 |

## 四、结论

**借鉴度 ★★ 中（理念印证为主）**。它是"视觉 AI + 多协议采集融合网关"的商业开源产品，
与我们"电流信号诊断"定位部分重合但不完全相同。最有价值的不是它本身，而是**三个行业共识的再次印证**：
① 断网续传（数据飞轮上行）；② 多协议统一接入（遥测驱动抽象）；③ **误报反馈闭环（我们数据飞轮理念的现成落地形态）**。
契合度略低于 edgeCore，但高于 cube-studio / star-edge-cloud。
